# 四阶段 Week Report 教程化要求大纲

## 1. 目标与读者

目标不是把实验日志写长，而是让一名具备基础 Python/C++ 能力、但第一次接触 Camera ISP/AI-ISP 的学习者，只沿着 Week 报告就能回答：从什么问题开始、输入是什么、为什么选这个方法、参数控制什么、如何运行、怎样判断结果、失败时先查哪里，以及面试时怎样准确表达。

报告必须同时服务三类读者：

1. 初学者：建立背景、术语和数据流，不依赖作者口头补充；
2. 实践者：能够按命令复现，并知道每一步的成功/失败信号；
3. 面试者：能从现象追到机制、参数、证据和边界，不只背定义。

## 2. 每篇主线 Week 报告的必备结构

每篇主线报告至少覆盖以下十项；已有等价章节时不要求机械改名。

| 编号 | 必备内容 | 必须回答的问题 |
|---:|---|---|
| 1 | 本周定位与前置知识 | 上一周产出了什么？本周为什么现在做？ |
| 2 | 背景与问题定义 | 真实 Camera/训练/部署链路里遇到了什么问题？不处理会怎样？ |
| 3 | 数据与输入输出合同 | shape、layout、dtype、数值范围、颜色/线性域、路径和 split 是什么？ |
| 4 | 关键词与参数表 | 术语是什么意思？参数单位、作用方向、过小/过大症状和耦合关系是什么？ |
| 5 | 原理与设计理由 | 公式/机制是什么？为什么选择当前 baseline？有哪些替代方案？ |
| 6 | 从零执行流程 | 环境检查、命令、代码入口、中间产物和最终产物按什么顺序出现？ |
| 7 | 验证与结果解读 | 先预测什么？看哪些数值/图片？结果支持什么、不支持什么？ |
| 8 | 故障诊断与权衡 | 第一发散点在哪里？质量、延迟、内存、复杂度如何取舍？ |
| 9 | 本周边界与下一周 | 哪些是 public/synthetic/proxy/not_run？输出如何成为下一周输入？ |
| 10 | 面试题与参考回答 | 至少包含定义题、机制题、参数题、实验设计题、故障题各一类。 |

## 3. 关键词与参数的写法

参数不能只写默认值。每个关键参数至少用下面五列解释：

| 参数/关键词 | 定义与单位 | 为什么存在 | 调大/调小会怎样 | 如何验证 |
|---|---|---|---|---|

例如 `sigma_range=0.1` 必须同时说明输入已归一化到 `[0,1]`；离开数值域谈阈值没有意义。`FP16`、`INT8`、`stride`、`patch_size`、`black_level`、`p50/p90` 等也必须写清量纲或统计口径。

需要显式区分容易混淆的概念：

- RAW 码值、线性 RGB、sRGB 显示编码；
- loss、metric、主观视觉判断；
- validation 选型、held-out test 最终验收；
- Python/C++ 数值对齐、算法质量、端到端性能；
- host tensor、device tensor、H2D/D2H、kernel/inference/e2e；
- synthetic、public dataset、self-capture、production evidence。

## 4. 实验叙事标准

每个实验按固定因果链描述：

```text
问题/现象
  -> 可证伪假设
  -> 只改变一个主变量
  -> 冻结输入、split、seed、指标和环境
  -> 运行并保存中间产物
  -> 用数值 + ROI/图像验证
  -> 记录失败案例
  -> 得出有限结论与下一步
```

禁止只写“运行脚本得到图片”，也禁止从一个数字直接跳到产品结论。报告要说明为什么选择该输入、为什么用该指标、为什么阈值合理，以及如果结果相反应如何解释。

## 5. 结果与证据边界

所有结果使用以下证据级别之一，并在报告中写明：

| 状态 | 含义 |
|---|---|
| `verified` / `verified_learning` | 在声明的代码、数据和环境中运行并验证；学习工程结论不等于量产结论 |
| `verified_proxy` | 指标或数据是可复现 proxy，不能替代标准实验室测量 |
| `verified_public_rgb` | 公开配对 RGB 结果，不能改写为 Sensor RAW 或自采 Camera 结果 |
| `verified_synthetic` | 合成向量/场景正确性，不能改写为实拍鲁棒性 |
| `verified_partial` | 链路只验证了一部分，缺失字段保持空值 |
| `not_run` | 没有对应数据、硬件或实测，不允许用计划值填充 |

实验数字必须能回指 CSV/JSON、测试输出或图像。历史协议不同的数字不得强行放进同一排行榜。

## 6. 面试题标准

每个 Week 至少准备五类问题，并给出“结论—原因—证据—边界”的参考回答：

1. 定义题：这个术语是什么，与相邻概念有什么区别？
2. 机制题：为什么算法/系统会产生当前现象？
3. 参数题：参数的量纲、调节方向、失败症状和选择依据是什么？
4. 实验题：怎样设计公平实验验证假设？
5. 故障题：结果错了或性能没提升，按什么顺序定位？

回答不能只有一句定义。推荐结构：

```text
先给结论
-> 解释机制
-> 引用本周实验或测试
-> 说明没有证明什么
```

## 8. 完成判定

一篇报告只有同时满足以下条件才算教程化完成：

- 不打开源码也能画出本周输入到输出的数据流；
- 能解释至少五个关键词或关键参数，而不是只列默认值；
- 命令、文件和产物路径存在，或明确标成计划/`not_run`；
- 结果包含指标口径、环境和边界；
- 至少一个失败案例或故障注入能回到第一发散点；
- 面试题覆盖定义、机制、参数、实验和故障五类；
- 能说清本周输出怎样进入下一周；
- 文档链接、代码测试和生成脚本不会因教程改动而失效。
